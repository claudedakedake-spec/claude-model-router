# model-router

[English](README.md) · **한국어**

큰 요청을 작은 작업으로 나누고, 각 작업을 **그 일을 잘 해낼 수 있는 가장 싼 Claude 모델**에게 맡기는 Claude Code 스킬입니다. 품질은 그대로 두고 사용량 한도는 덜 쓰는 것이 목표입니다.

> **핵심 원칙:** *비싼 모델이 정하고, 싼 모델이 만든다.*
> 강한 모델(Opus, Fable)이 어려운 판단을 하고 명확한 명세를 씁니다. 싼 모델(Sonnet, Pro에서는 Haiku까지)이 그 명세대로 손이 많이 가는 일을 합니다. 모든 결과는 확인을 거쳐야 인정됩니다.

## 왜 만들었나

Claude Code를 쓰는 흔한 방식은 두 가지인데, 둘 다 뭔가를 낭비합니다.

- **전부 가장 큰 모델로 하는 경우:** 품질은 좋습니다. 하지만 파일 찾기, 반복 수정, 뻔한 코드 같은 단순한 일까지 비싼 모델이 해서 5시간 한도와 주간 한도가 금방 닳습니다.
- **전부 작은 모델로 하는 경우:** 토큰당 값은 쌉니다. 하지만 어려운 부분을 틀리기 쉬워서 고치고 다시 하는 비용이 들고, 어떤 버그는 아무도 모르게 지나갑니다.

이 스킬은 경험 많은 개발 리더처럼 일합니다. 일을 알맞은 사람에게 나눠 주고, 지시를 분명하게 쓰고, 돌아온 결과를 전부 확인합니다.

## 요금제에 맞는 버전 고르기

저장소에 플러그인이 두 개 들어 있습니다. **내 요금제에 맞는 것 하나만** 설치하세요.

| | **model-router** | **model-router-pro** |
|---|---|---|
| 대상 | Claude **Max / Ultra** | Claude **Pro** |
| 쓰는 모델 | Sonnet → Opus → Fable | Haiku → Sonnet → Opus |
| Haiku | 안 씀. 품질이 우선이라 Sonnet이 가장 낮은 단계 | 단순 조사 담당 "정찰병"으로 씀 |
| Fable | 가장 어려운 문제에 씀 | 사용자가 승인할 때만. Pro는 Fable이 기본 사용량에 포함되지 않아 추가 사용량 크레딧으로 결제됨 |
| 우선순위 | 품질 우선, 그 안에서 절약 | 빠듯한 Pro 한도를 최대한 오래 쓰기 |

## 설치

### 방법 A: 플러그인으로 설치 (추천)

Claude Code 안에서 입력합니다.

```
/plugin marketplace add claudedakedake-spec/claude-model-router

# Max / Ultra
/plugin install model-router@model-router

# Pro
/plugin install model-router-pro@model-router
```

한 번 설치하면 모든 프로젝트에서 작동합니다.

### 방법 B: 내려받은 폴더를 연결

```sh
git clone https://github.com/claudedakedake-spec/claude-model-router.git
cd claude-model-router
```

```powershell
# Windows (폴더 연결(junction)을 만듭니다. 관리자 권한 필요 없음)
./install.ps1        # Max / Ultra
./install.ps1 pro    # Pro
```

```sh
# macOS / Linux (심볼릭 링크를 만듭니다)
sh install.sh        # Max / Ultra
sh install.sh pro    # Pro
```

스킬을 `~/.claude/skills/`에 연결하는 방식이라, 내려받은 폴더의 파일을 고치면 바로 반영됩니다.

> ⚠️ 두 방법 중 **하나만** 쓰세요. 둘 다 하면 스킬이 두 번 나타납니다.

## 쓰는 법

**저절로 켜지는 경우:**
- 여러 작업을 한 번에 시킬 때. 큰 기능, 리팩터링, 버그 여러 개 수정, 조사 후 구현 같은 요청입니다.
- 토큰, 비용, 한도, 속도, 효율, "어떤 모델" 같은 말을 할 때.

**직접 부르기:** 모드를 붙일 수도 있습니다.

```
/model-router                       # Max / Ultra, 기본(balanced) 모드
/model-router eco 다크 모드 추가하고 로그인 버그 고쳐줘
/model-router-pro quality 설정 화면 다시 디자인해줘
```

파일 하나 고치기나 짧은 질문 같은 작은 요청은 나누지 않고 바로 처리합니다. 그런 일은 나누는 비용이 아끼는 양보다 큽니다.

## 실제로 보이는 것

작업이 3개 이상으로 나뉘면 먼저 이런 계획표를 보여 주고 바로 진행합니다.

```
| 작업                              | 모델   | effort | 이유                          |
|-----------------------------------|--------|--------|-------------------------------|
| 옛 로그인 API를 부르는 곳 전부 찾기 | Sonnet | low    | 검색, 확인 쉬움               |
| 새 세션/토큰 구조 설계             | Opus   | high   | 구조 결정, 보안               |
| 14곳의 호출부를 새 API로 수정      | Sonnet | medium | 같은 수정 반복, 명세 분명     |
| 전체 변경 검토                     | Opus   | high   | 숨는 보안 버그는 비쌈         |
```

끝나면 실제로 어떤 작업을 어떤 모델로 돌렸는지, 윗단계로 올린 작업이 있었는지 표로 보고합니다.

## 모델을 고르는 방법

### 모델 단계

| 단계 | 주로 맡는 일 | effort |
|---|---|---|
| **Haiku** *(Pro만)* | 파일과 함수 찾기, 목록 만들기, 로그나 문서에서 사실 뽑기, 간단한 요약 | low |
| **Sonnet** *(기본)* | 정해진 명세대로 구현, 여러 파일의 반복 수정, 설명을 보고 UI 만들기, 테스트, 스크립트, 질문이 정해진 조사. Max에서는 조사도 맡음 | low~medium |
| **Opus** | 어려운 설계, 원인 모를 버그, 리팩터링, 위험한 변경 검토. Max에서는 설계 판단이 필요한 여러 파일 기능도 맡음 | medium~high |
| **Fable** *(Max/Ultra)* | 새 시스템 구조, 매우 모호한 문제, 미묘한 정확성 문제(동시성, 네트워크 동기화, 보안, 데이터 무결성), Opus가 두 번 실패한 문제 | high |

### 작업마다 던지는 질문

모든 작업은 Sonnet에서 출발하고, 다섯 가지를 따집니다.

1. **"끝났다"의 기준이 모호한가?** 목표가 흐릿하거나 취향 판단이 필요하면 판단력이 더 필요합니다.
2. **진짜 추론이 필요한가?** 새 구조, 까다로운 규칙, 원인 모를 문제처럼, 단순히 많이 치는 일이 아닌 경우입니다.
3. **영향 범위가 넓은가?** 단단히 얽힌 여러 파일, 서버 로직, 저장 데이터, 로그인, 결제 등입니다.
4. **틀리면 비싸거나 알아채기 어려운가?** 테스트로 안 잡히는 버그가 여기 해당합니다.
5. **대부분 양의 문제인가?** 손이 많이 가는 반복 작업은 싼 모델이 가장 많이 아끼는 곳입니다.

1~4번에 "예"가 나올수록 강한 모델로 올라갑니다. 5번만 "예"면 싼 모델에 둡니다. **길다거나 파일이 많다는 것만으로는 큰 모델을 쓸 이유가 안 됩니다.** 단단히 얽혀 있거나, 실수가 조용히 숨을 수 있을 때가 이유가 됩니다.

### 직접 할지, 맡길지

도우미 에이전트(서브에이전트)는 아무것도 모르는 상태에서 시작합니다. 지시를 받아야 하고 파일도 다시 읽어야 합니다. 그래서 몇 단계면 끝나는 일, 지금까지의 대화 내용이 필요한 일, 사용자와 주고받으며 해야 하는 일은 메인 대화에서 직접 합니다. 크고 따로 떼어 낼 수 있는 일, 다른 모델로 하면 훨씬 싼 일만 맡깁니다.

## 구현 품질 기준

**싼 모델은 한 번에 맞힐 때만 쌉니다.** 그래서 스킬은 모델 값만 보지 않고 **예상 총비용**을 비교합니다. 예상 총비용은 "모델 값 × 시도 횟수 + 놓친 버그 비용"입니다.

**Sonnet이 코드를 쓰는 경우:**
- 무엇을 어떻게 바꾸고 어떻게 확인할지 명세에 정확히 적혀 있을 때
- 따라 할 기존 패턴이 코드에 있을 때
- 한 곳만 고치거나, 같은 수정을 여러 곳에 반복할 때
- 실수가 바로 드러날 때 (테스트, 빌드 오류, 화면)

**Opus가 코드를 쓰는 경우 (하나라도 해당하면):**
- 명세에 해석이 필요할 때 ("타격감 있게")
- 단단히 얽힌 부분이 서로 어긋나면 안 될 때 (클라이언트와 서버, 공유 상태, 통신 규약)
- 실수가 조용히 숨을 때 (동기화 어긋남, 경쟁 상태, 게임 규칙 버그, 보안, 데이터 손실)
- 지켜야 할 조건이 많은 긴 작업일 때
- 다른 코드가 전부 기대는 핵심 부분일 때 (엔진 루프, 데이터 구조, 네트워크 코드)

**Fable이 코드를 쓰는 경우**는 Opus가 짠 코드조차 위험할 때뿐입니다. 새로운 알고리즘이나 미묘한 동시성 핵심 코드 같은 경우입니다. 그 밖에는 Fable이 설계와 검토만 맡습니다.

### 나눠 맡겨도 품질이 고르게

한 작업에 어려운 부분과 반복 부분이 섞여 있으면, 강한 모델이 어려운 부분을 하고 Sonnet은 그 예시를 따라 합니다. 그런데 단순히 "첫 번째를 따라 해라"로 나누면 1번만 좋고 나머지는 밋밋해질 수 있습니다. 그래서 세 가지 규칙을 따릅니다.

1. **판단은 강한 모델이 미리 전부 합니다.** 항목마다 동작, 느낌, 수치, 연출, 예외 상황을 명세로 씁니다. Sonnet은 명세를 코드로 옮기기만 합니다.
2. **새 메커니즘이 있는 항목은 따라 하기 대상이 아닙니다.** 첫 번째에 없는 시스템이 필요하면 그것도 강한 모델이 만듭니다.
3. **마지막에 전체를 나란히 놓고 검토합니다.** 첫 번째보다 못한 것은 고치거나 다시 맡깁니다.

**예시: 게임 술법 10개 만들기**

| 작업 | 모델 |
|---|---|
| 술법 10개 전부의 명세 (동작, 느낌, 수치, 연출, 예외 상황) | Opus |
| 술법 입력 시스템 + 첫 번째 발사형 술법을 처음부터 끝까지 | Opus |
| 분신술, 은신술 (새 메커니즘) | Opus |
| 나머지 발사형·범위형 술법 (같은 구조, 명세대로) | Sonnet 여러 개 동시 |
| 10개 전체 비교 검토 + 멀티플레이 동기화 검토 | Opus |

**작업하면서 배웁니다.** 같은 종류의 일에서 Sonnet이 두 번 이상 고치고 다시 했다면, 남은 같은 종류는 처음부터 Opus가 맡습니다. 반대로 Opus가 너무 쉽게 해내는 종류는 Sonnet으로 내립니다.

## 실패했을 때 (단계 올리기)

모든 결과를 확인합니다. 테스트를 돌리고, 화면을 열어 보고, 변경 내용을 읽습니다. 도우미 에이전트는 틀려도 자신 있게 말하기 때문에, 이 확인 덕분에 싼 모델을 안심하고 쓸 수 있습니다.

```
Max / Ultra:
  Sonnet ─실패→ Sonnet 재시도 (실패 내용 추가) ─실패→ Opus ─2번 실패→ Fable

Pro:
  Haiku ─결과 부족→ Sonnet (Haiku 재시도 없음)
  Sonnet ─실패→ Sonnet 재시도 (실패 내용 추가) ─실패→ Opus ─2번 실패→ 멈추고 사용자에게 물어봄
```

Pro에서 Opus가 두 번 실패하면 같은 시도를 반복하지 않고 멈춥니다. 무엇이 불분명한지 설명하고 세 가지 선택지를 드립니다. 정보를 더 주시거나, 범위를 좁히시거나, Fable을 추가 요금으로 승인하시는 것입니다.

## 자동으로 정해 주는 설정

| 설정 | 스킬이 하는 일 |
|---|---|
| 도우미 작업별 **effort** | 자동으로 정합니다. 조사와 단순 수정은 낮게, 설계와 디버깅은 높게, 재시도할 때는 한 단계 올립니다 |
| **plan 모드** | 크거나 모호한 작업(3개 이상, 구조 결정, 파일 다수)이면 스스로 plan 모드에 들어갑니다. 수정 없이 조사만 하고, 모델 배분표를 담은 계획을 보여 드린 뒤 승인을 받습니다. 작은 작업은 건너뜁니다 |
| **auto / 권한 모드** | Claude가 켤 수 **없습니다**. 사용자의 안전을 위한 선택이기 때문입니다. 승인된 계획에 단순 수정이 많아 허락 요청이 계속 끼어들면, Shift+Tab으로 바꾸시라고 한 번 권합니다. 배포, 삭제, 외부 공개 작업에서는 권하지 않습니다 |
| **메인 대화 모델** | `/model`로 사용자만 바꿀 수 있습니다. 설계가 끝나고 반복 구현으로 넘어가는 식으로 작업 성격이 바뀌면, 바꾸시라고 한 줄로 권합니다 |

## 모드

| 모드 | Max / Ultra (`model-router`) | Pro (`model-router-pro`) |
|---|---|---|
| `eco` | 모든 작업을 한 단계 낮게 시작 (Sonnet이 최저). Fable은 Opus가 실패한 뒤에만 | Opus는 Sonnet이 두 번 실패했을 때나, 위험한 변경의 마지막 검토 한 번에만 |
| `balanced` *(기본)* | 단계 표 그대로 | Opus는 어려운 설계, 원인 모를 버그, 위험한 변경 검토에 |
| `quality` | 설계, 디버깅, 검토는 한 단계 높게. 단순 작업은 그대로 싸게 | 설계 판단이 필요한 여러 파일 기능도 처음부터 Opus에 |

## Pro 전용 절약 규칙

- **가장 좋은 구성은 메인 대화를 Sonnet으로 두는 것**입니다. Opus는 어려운 부분에만 도우미로 부릅니다. 메인이 Opus면 `/model sonnet`을 한 번 권합니다. 계획할 때는 Opus, 실행할 때는 Sonnet을 쓰는 `/model opusplan`도 권합니다.
- **도우미는 한 번에 3개 정도만 돌립니다.** 한꺼번에 많이 돌리면 결과를 확인하기도 전에 5시간 한도에 닿을 수 있습니다.
- **Opus에게는 가장 값진 일인 명세 작성을 맡깁니다.** 명세를 한 번에 다 쓰는 Opus 호출 하나가, 코드를 치는 Opus 호출 여러 번보다 값집니다.
- **보고는 짧게 받습니다.** 도우미 보고도 토큰이라서, 긴 설명 대신 경로, 변경 내용, 발견한 것만 받습니다.
- **세션 길이를 챙깁니다.** 남은 사용량은 Claude가 볼 수 없습니다. 그래서 세션이 길어지면 단계를 마무리하고 새 세션에서 이어 가거나 `/usage`를 확인하시라고 권합니다.

## 한계

믿고 쓰시기 전에 꼭 읽어 주세요.

- **메인 대화의 모델은 바꿀 수 없습니다.** Claude Code가 허용하지 않기 때문입니다. `/model`로 사용자만 바꿀 수 있습니다. 스킬은 다른 모델의 도우미 에이전트에게 작업을 맡기는 방식으로 나눕니다.
- **모델별 한도 차감 비율은 공개되어 있지 않습니다.** 그래서 정확한 숫자 대신 단계로 판단합니다.
- **아직 벤치마크하지 않았습니다.** 배분 규칙은 모델 등급별 일반적인 경향에 근거한 것이고, 같은 작업으로 직접 비교해 측정한 것은 아닙니다. `/usage`를 작업 전후에 확인하시면 직접 측정할 수 있습니다.
- **`CLAUDE_CODE_SUBAGENT_MODEL` 환경 변수가 있으면** 스킬이 고른 도우미 모델보다 그 값이 우선합니다.
- **Pro 버전은 아직 실제 Pro 계정에서 시험하지 않았습니다.** `opusplan`은 Claude Code 버전에 따라 없을 수 있습니다.
- **도우미 에이전트에도 비용이 듭니다.** 지시를 쓰고 파일을 다시 읽는 부담이 있어서 작은 작업은 나누지 않습니다.

## 자주 묻는 질문

**Claude가 느려지나요?**
큰 작업에서는 서로 상관없는 부분을 동시에 돌려서 보통 더 빠릅니다. 작은 작업은 나누지 않으니 달라지는 게 없습니다.

**Max 버전에는 왜 Haiku가 없나요?**
Max에서는 싼 모델이 실패해서 다시 하는 비용이 Haiku로 아끼는 양보다 크고, 품질이 우선이기 때문입니다. Pro는 한도가 빠듯해서 범위가 좁은 조사에는 Haiku가 이득입니다.

**허락 없이 Fable을 쓰나요?**
Max/Ultra에서는 씁니다. 다만 Fable 단계에 맞는 문제이거나 Opus가 두 번 실패했을 때만입니다. Pro에서는 절대 쓰지 않고 항상 먼저 물어봅니다.

**무엇을 어떻게 정했는지 볼 수 있나요?**
네. 큰 작업은 시작 전에 배분 계획을, 끝난 뒤에 요약 표를 보여 줍니다.
